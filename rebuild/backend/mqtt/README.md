# MQTT ingestion (T13 backend slice)

T14 adds command dispatch and correlated result admission to this same singleton
worker. See [commands](../features/commands/README.md). Live dispatch additionally
requires process setting `BB_MQTT_COMMANDS_QUALIFIED=true` after command ACL
qualification; ordinary ingestion works with it false. Use `python -m
backend.mqtt.qualify --commands` after the T14 role change. Older T13/T13A
command-denial descriptions below retain their original historical scope.

This is a separate process, using the existing PostgreSQL database and T02 wire
contracts. API startup never connects to MQTT. Firmware/cloud changes and real
ESP32/HiveMQ acceptance are not included; live operation defaults to disabled.

## Run and private configuration

From rebuild, using the pinned backend environment:

```powershell
.\backend\.venv\Scripts\python.exe -m backend.mqtt
```

With no MQTT configuration this prints `MQTT ingestion disabled; no connections
opened` and exits. API run.cmd, port, auth/database private settings and health are
unchanged. No table creation, migration or account/device enrollment occurs at
worker startup. Apply migration 0005_t13 explicitly through backend.database.migrate.

MQTT reads only process BB_MQTT_* variables and the ignored backend/mqtt/.env.
The adjacent .env.example has no secrets and remains disabled. It does not load
the prototype or backend authentication .env. Database settings still come from
the existing isolated rebuild database configuration.

| Setting | Behavior |
|---|---|
| MODE | disabled/default, test, live |
| HOST / PORT | Broker endpoint; example loopback port 58883 |
| PREFIX | Default bangusbuhai-rebuild; 1..64 ASCII letters/digits/_/- |
| CLIENT_ID | Stable identity per worker; default bb-rebuild-ingestion |
| CA_FILE | Explicit trusted server CA PEM path |
| AUTH_MODE | certificate/default or password; both require verified TLS |
| CREDENTIAL_FILE | Password mode: private JSON with exactly username/password; outside Git |
| CERTIFICATE_FILE / KEY_FILE | Dedicated backend client identity; private key stays outside Git |
| BROKER_QUALIFIED / FIRMWARE_QUALIFIED | Both must be true to explicitly enable live mode |

Test mode requires a loopback broker and the exact dedicated test database. Use
the automated fixtures below rather than setting up test users or reusing real
device keys. Live qualification flags are owner-recorded release gates, not
automatic certification of hardware/cloud controls. Do not set them from a local
simulator pass. No live .env or certificates are generated by T13.

TLS requires client credentials, trusted server certificate, hostname validation,
TLS 1.2+ and strict X.509 validation. A small SSLContext adapter bounds the initial
handshake to five seconds and closes its socket on failure before passing it to
Paho 2.1.0; no verification bypass or dependency patch is used. Paho compatibility
is exercised on the recorded Python 3.14.6 runtime.

## Processing and admission

The worker subscribes at QoS 1 to PREFIX/devices/+/telemetry and /command-results.
It publishes only non-retained QoS 1 ACKs on PREFIX/devices/DEVICE/acks. Status,
commands and browser updates belong to other tasks.

Callbacks copy at most 4096 payload bytes and a 256-character topic to a bounded
64-entry queue. Oversize messages are dropped without database work or a success
ACK. A processing thread owns database work and returns outcomes through a second
bounded 64-entry completion queue. Only the network thread calls Paho, preventing
cross-thread socket/callback lock races. Sessions set ten-second statement
and five-second lock timeouts. Queued messages carry a connection generation;
stale generations cannot acknowledge after reconnect. Queue pressure, connection
loss and temporary processing failure trigger bounded 1..300-second reconnect
backoff. Counter summaries contain bounded reason codes/counts, never wire bodies,
certificates, keys or exception details. No per-payload logging is enabled.

One session-level PostgreSQL advisory lock per database/prefix protects the worker
namespace even with different host aliases/client IDs. Its reserved connection is
checked periodically and before publishing an application ACK. Connection loss
stops/fences the worker; it does not silently reacquire a potentially lost lock.
An external process supervisor can restart it after recovery. This is singleton
protection, not a certified high-availability or throughput design.

T02 rejects invalid JSON, duplicate keys, invalid versions/types, non-finite
numbers and invalid topic/device agreement. Structural parsing grants no binding
permission. The transaction locks hatchery, inventory and device in registry order,
refreshes state, verifies the pinned credential and checks the retained binding.
Validly formatted traffic never creates identities, ownership or assignments.

| Event case | Result |
|---|---|
| Already committed, identical normalized content | duplicate ACK after verified identity/content lookup, including closed/archived associations |
| Same device/boot/sequence, different content or kind | Quarantine event_conflict; never overwrite |
| Current active and confirmed binding | Accept telemetry; synchronized captures must be at/after binding start |
| Current binding with unknown capture time | Accept with explicit null time if active/current configuration is confirmed |
| Closed binding with retained confirmation | Accept only synchronized captures in [start,end), even when resources are now archived |
| Unknown/unconfirmed/foreign binding, uncertain closed capture | Quarantine; preserve original payload and attribution claims |
| Capture more than five minutes ahead of processing receipt | Quarantine; never infer a corrected timestamp |
| New command result | Quarantine command_context_unavailable until T14 supplies authorized command correlation |

Accepted telemetry uses existing persist_event and the atomic T12 history trigger.
Acquisition validity, default pH, sample ages, diagnostics, relay and nullable
capture time remain unchanged. Stored readings always retain the original binding
and tank. No quality classification or model eligibility is inferred.

T13 retains each successfully proved configuration document, digest, credential
fingerprint and confirmation time before a future desired revision replaces it.
Migration backfills only supported currently confirmed documents; it does not
reconstruct old confirmations from incomplete audit entries. An earlier binding
without retained proof remains quarantined. Device proof is still not physical
NVS evidence until the real firmware onboarding gate is verified.

## Two acknowledgement layers

MQTT PUBACK acknowledges broker delivery. T02 application ACK is what lets the
device release its durable event. Manual broker ACK occurs after processing,
including permanent rejection/quarantine, to avoid poisoning broker redelivery.
Rejected/quarantined events receive no application success ACK.

service.process exits its database transaction before returning a stored/duplicate
ACK candidate. A commit failure returns none. The worker checks its generation and
lease, then publishes. If publication/response is lost after commit, the device
retries and receives duplicate; no second event or T12 journal entry is created.
There is no independent ACK outbox: recovery relies on the device's existing
durable retry contract. MQTT delivery alone never proves database commit.

## Quarantine and inspection

Schema-valid candidates retain canonical content, device/boot/sequence, kind,
SHA-256 digest, bounded reason and first server receipt. Identical candidates are
deduplicated; conflicting variants are retained separately. Content/evidence is
immutable at the database boundary. A later admissible retry may enter normal
history while its earlier quarantine evidence remains; nothing is relabelled.

Capacity is 1000 candidates per external device ID and 10000 globally, serialized
under a separate transaction advisory lock. At capacity new uncertain candidates
are rejected without storage or success ACK; admissible traffic still works.
No automated eviction, release, deletion or public inspection endpoint is added.
Retention/resolution policy needs separate owner-scoped work.

Trusted local read-only inspection defaults to the isolated development database:

```powershell
.\backend\.venv\Scripts\python.exe -m backend.mqtt.inspect --limit 50
.\backend\.venv\Scripts\python.exe -m backend.mqtt.inspect --device BB-AABBCC112233 --payload
```

Use --test for the dedicated test database and --cursor for the returned
next_cursor. Limit is 1..200. Payload display is explicit; JSON output escapes
untrusted strings. With today's firmware an uncertain queue-head event can hold
up later readings and eventually encounter the existing finite-buffer policy.
Do not send a fake success ACK to make the queue drain.

## Verification and live boundary

From rebuild:

```powershell
.\backend\.venv\Scripts\python.exe -m unittest discover -s backend/tests -t . -v
.\check.cmd
```

Database and broker tests require Docker/PostgreSQL; missing prerequisites fail
rather than silently skip. Fixtures create random t13_test schemas, a separately
named loopback Mosquitto container and temporary generated certificate files.
They never mount or read real device credentials. The broker image is pinned to:

```text
eclipse-mosquitto@sha256:38c0da4f2ef84284d47b3b3eeea1cb3bdeabe81ee10caf0cd5c5ff61ee3ea408
```

Mosquitto is a disposable test fixture; HiveMQ remains the selected live broker.
The fixture disables all retained messages and maps certificate CN to ACL identity.
Its file ACL authorizes message delivery, so a broad filter can receive SUBACK
while forbidden traffic is still blocked. Tests prove actual cross-device/ACK
delivery isolation with positive controls; they do not claim HiveMQ SUBACK,
retained-status, revocation or account capability qualification.

Before live enablement, verify a separate backend certificate/role, device-to-topic
binding and denied device ACK/command publication on the actual HiveMQ service.
Ordinary subscribed packets do not expose the publisher's certificate: broker
ACLs are an essential trust boundary. Do not share a device key with the backend,
broaden device roles or infer authorization from a self-reported client ID.

Real firmware must prove identity, persist runtime binding/configuration, confirm
the exact revision/digest and recover interrupted setup before live admission.
The current fixture binding and pre-claim queue are not silently enrolled/imported.
T07's existing gaps and deferred BOOT-button work remain unchanged. Live-provider,
hosted-CI and local evidence are separately recorded in the T13 handoff.

## T13A custody extension

T13A adds QuarantineReceipt on PREFIX/devices/DEVICE/quarantine-receipts, QoS 1,
non-retained. Only committed quarantine content from a verified owned telemetry
device receives one. It identifies quarantine_id, original reason, event identity
and SHA-256 of the exact wire bytes. It is not a stored/duplicate ACK and does
not place the event in tank history. Capacity/commit/invalid-device failures
still receive no application response. Retries reuse the semantic custody record;
each response hashes the current exact retry bytes. Firmware only releases an
exact pending head match. Old firmware ignores the new topic.

Qualify backend-only publication and per-device subscription alongside acks.
Do not reuse the ESP32 key. Configurations default to `disabled` with both gates
false. This specific T13A lab is now qualified/enabled after actual device and
broker checks (2026-10-22); ordinary ingestion runs and the lost-ACK worker is
stopped. No other deployment inherits that qualification. See the
[device guide](../../firmware/components/device_setup/README.md) and T13A handoff.
For the explicit local lost-ACK checkpoint use `python -m backend.mqtt.verify_live`
instead of the normal worker, with normal live qualification gates still enforced.
It suppresses exactly the first stored response after commit, without suppressing
quarantine receipts or later duplicates. It accepts only the existing loopback
55432 development database. Never run both workers for the same prefix.
